# Формат каталога

Основной доступ: `buildings[ID]`. Не нужно просматривать весь JSON, чтобы получить требования одного здания.

```python
import json
from pathlib import Path

catalog = json.loads(Path('data/buildings-agot.json').read_text(encoding='utf-8'))
building = catalog['buildings']['caravanserai_01']
print(building['construction_cost']['resolved_base_cost'])  # {'gold': 200}
for block in building['requirements']['can_construct']:
    print(block['script'])
```

## Пять категорий

Раздел `categories` содержит пять групп с русским названием `name`, исходными типами игры `source_types` и списком ID `building_ids`:

| Ключ | Название | Исходный `type` |
|---|---|---|
| `base` | Базовые постройки | Основные здания владений и их улучшения; сейчас имеют тип `regular` |
| `regular` | Обычные здания | `regular`, кроме базовых |
| `duchy` | Герцогские постройки | `duchy_capital` |
| `special` | Особые постройки | `special` |
| `great` | Великие постройки | `great_building` |

Каждое здание входит ровно в одну группу. Его поле `category` указывает на эту группу; `type` сохраняет исходный тип игры. Количества по пяти группам находятся в `summary.by_category`.

Категория `base` определяется первой: в `holding_memberships` должна быть роль `primary_building`. Она наследуется всеми уровнями цепочки от здания, указанного как основное в определении владения. Это охватывает замки, города, храмы, монастыри и основные постройки остальных типов владений; совпадения названия или принадлежности к дополнительным зданиям замка недостаточно. В метаданных группы это обозначено полем `membership_role`. Если такой роли нет, категория определяется по `type`.

```python
for building_id in catalog['categories']['special']['building_ids']:
    building = catalog['buildings'][building_id]
    print(building_id, building['construction_cost']['resolved_base_cost'])
```

Категория не отменяет требований строительства. Великие постройки сохраняют свои ссылки на проекты. Основные здания технических владений входят в базовые; остальные технические объекты классифицированы по исходному типу. Для отбора построек будущего интерфейса нужно учитывать `is_graphical_background`, `explicit_potential_always_no` и условия.

## Узлы условий

Блок `AND = { ... }` представлен так:

```json
{
  "key": "AND",
  "operator": "=",
  "children": [
    { "key": "is_county_capital", "operator": "=", "value": "yes" },
    { "key": "has_building_or_higher", "operator": "=", "value": "castle_01" }
  ]
}
```

`value` хранит **исходный токен строкой**, включая ведущие нули и кавычки. Числовые цены вынесены в `base_value` отдельно. Узел содержит либо `value`, либо `children`. Список упорядочен; одинаковые `key` разрешены.

`operator` может быть `=`, `?=`, `<`, `>`, `<=`, `>=`, `!=`, `==` или `null` для элемента списка. Дополнительный `prefix` применяется к типизированным блокам и явно неполным данным источника.

Дерево синтаксическое, поэтому оно **не выдаёт любой вложенный блок за логическое И**:

- `OR`, `AND`, `NOT`, `NOR`, `NAND` остаются собственными операторами игры.
- `scope:holder`, `county`, `faith`, `culture` и другие переходы меняют область проверки.
- `trigger_if`/`trigger_else_if`/`trigger_else` сохраняются в исходном порядке, вместе с `limit`.
- `any_county_province` сохраняет свой `count`, а также проверяемые внутри свойства.
- `custom_tooltip`/`custom_description` сохраняют текстовую метаинформацию и сами условия.
- Необязательное `scope:holder ?= { ... }` не подменяется строгим `=`.

Отсутствующий блок требований — `[]`. Это означает «в этом определении нет явного блока», а не «строительство всегда разрешено».

## Общие проверки и параметры

Пример вызова:

```json
{
  "key": "building_requirement_castle_city_church",
  "operator": "=",
  "children": [
    { "key": "LEVEL", "operator": "=", "value": "01" }
  ],
  "definition_refs": [
    "scripted_trigger:building_requirement_castle_city_church"
  ]
}
```

Соответствующий элемент `definitions` содержит исходный скрипт, дерево, список параметров и источник. В нём остаются выражения `castle_$LEVEL$`, `city_$LEVEL$` и остальные альтернативы. При будущем исполнении параметр нужно подставить как `01`, а не `1`.

Для отрицательного вызова `building_requirement_tribal = no` ссылка ведёт к той же проверке, но `value` остаётся `no`. Удалять его при раскрытии определения нельзя.

Ссылки образуют граф. Рекурсивные ссылки не разворачиваются бесконечно; потребитель должен учитывать уже посещённые определения. Динамические флаги, параметры культур, государственные формы и другие нативные предикаты остаются в скрипте. Каталог не пытается воспроизвести всё состояние мира в JSON.

## Цены

`construction_cost.entries` сохраняет только первое присваивание для каждой валюты, в порядке чтения. Это правило выбрано пользователем и применяется как к различающимся, так и к одинаковым повторным ценам. У записи есть:

- `currency` — валюта;
- `script`, `syntax`, `source` — точное выражение и его происхождение;
- `status = constant` и числовой `base_value`, если вычислена константа;
- `status = requires_context_or_review`, `base_value = null` и причина — для динамического либо неподдержанного расчёта.

`resolved_base_cost` содержит выбранную первую цену по каждой валюте. Последующие присваивания в `entries` не попадают и не суммируются. `repeated_currency_fields` перечисляет валюты, для которых удалены повторы; вторые значения не сохраняются. Например, у `agot_midges_inn_01` и `agot_ormyan_palace_01` оставлено по 200 золота.

`status = not_declared`, пустые `entries` и `{}` в `resolved_base_cost` означают отсутствие обычной цены в определении, а не бесплатную постройку. На текущем срезе все выбранные записи обычной цены постоянны.

Цены восстановления — `rebuild_cost`; здесь могут встречаться ветви для ИИ/игрока и зависимость от дохода. Полное дерево такого расчёта сохраняется даже если единственное число получить нельзя.

## Цепочки и доступность

`upgrade.chains` — список пар `root`/`level`, а не один предполагаемый номер из суффикса. У большинства зданий цепочка одна. У `agot_bitterbridge_02` две исходные ветви сходятся на одном уровне; обе сохранены.

`holding_memberships` перечисляет включение цепочки в определения владений: `role = primary_building` или `buildings`. У особых зданий пустой список здесь нормален: их доступность определяется специальными ячейками и скриптами.

`history_assignments_exact_id` хранит назначения именно этого ID. `history_assignments_chain_roots` помогает найти ячейку, исторически объявленную для первого уровня цепочки. `history_path` сохраняет исходные даты, не выбирая стартовую закладку за пользователя.

Для великих проектов `great_project_upgrade_pointer` и `great_projects_granting_this_building` различаются: первый — ссылка интерфейса здания, второе — проекты с прямым эффектом выдачи данного здания. Их полные определения доступны по `great_project_definition_refs`.

## Происхождение и переопределения

`source.layer` ссылается на `layers`, а у вспомогательных названий также на `extra_name_layers`. `source.path` — путь относительно корня источника, `source.line` начинается с 1. `source_files` содержит SHA-256 прочитанных скриптов для определения версии среза.

Замены целых файлов отражены в `diagnostics.file_overrides`. Повторные ID в разных файлах — в `duplicate_definitions`, полные варианты — в `duplicate_candidates`. Статически выбранный вариант такого здания отмечен `definition_selection_status = provisional_duplicate_id`; это не утверждение о проверенном в работающей игре выборе движка.

Сравнение каталогов отдельно показывает изменения общих определений: тело здания может совпасть, а вызываемый им триггер измениться. Например, в текущей сборке так происходит с `building_quarries_requirement_terrain`.
